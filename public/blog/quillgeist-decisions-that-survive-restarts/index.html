Making Quillgeist More Reliable

How I extended Quillgeist with durable local planning and optional decision-model routing, and why operational judgment matters more than adding another model.

By Clinton Kosh · Implementation note

I added persistent local plans and an optional decision-model adapter to Quillgeist. These changes give interrupted work a recovery path and prepare the router to use decision models for bounded choices.

Two releases sharpened the design

Cloudflare's Clef announcement describes decision models that score permitted choices instead of generating prose. Cloudflare publishes Clef and Clef-flash under Apache 2.0 and describes Jev API compatibility. That makes them candidates for bounded routing decisions before a larger model reasons about a task.

Earendil's Pi Durable release approaches the other half: Making agent work survive interruptions. Its experimental status matters. I adopted durability principles through a native local interface rather than making every project depend directly on a new API.

What I changed

I extended Quillgeist's existing local execution architecture in three places.

First, preserve the plan. Big-prompt planning now ingests its output into a machine-local SQLite harness. The harness records request identity and a content fingerprint, rejects conflicting reuse, supports atomic worker claims, preserves checkpoints, and fences stale workers from committing after ownership changes. Its event journal makes state transitions inspectable.

Second, make decision providers replaceable. The existing router now accepts optional Clef-flash and Clef classifiers alongside its earlier options. A bounded loopback adapter validates choices and probabilities, limits response size, and enforces a timeout. Missing or malformed model output can fall back to the existing local path.

Third, keep authority ahead of model preference. I corrected the router so a known external-authority requirement is evaluated before an explicit model override. Selecting a local model must never turn publishing, private account access, or another consequential action into an ordinary local task.

Recovery needs judgment

Duplicate submission protection is useful. It is not a guarantee that every external action happens exactly once.

If a read-only calculation stops, retrying may be straightforward. If a process stops after sending an external request but before saving the response, its outcome may be unknown. Repeating it could create duplicate work.

The native harness therefore distinguishes replay-safe work from interrupted effects that need reconciliation. Retry limits and ownership checks are part of the implementation. That is the same judgment I would apply to a customer escalation: Recover what is recoverable, establish what happened, and avoid creating a second problem while fixing the first.

What the tests establish

The initial repository validation passed 26 checks across the new durability and routing tests and existing prompt-planning suites. Coverage includes duplicate request handling, workspace separation, concurrent claims, checkpoint recovery, stale-worker rejection, retry bounds, and authority precedence. A reviewed machine smoke task exercises the new recovery path using a temporary database.

These results establish repository behavior in the build environment. They do not establish that Clef is serving on my Windows machines or that every existing QQ task has migrated to checkpointed execution.

What still needs proof

Live Clef inference, per-task confidence calibration, and migration of the existing runner's task lifecycle remain rollout gates. No Pi Durable backend is installed in this change; the current implementation is native. The Clef adapter is an integration boundary, not a deployed model.

Hardware fit also comes first. Clef-flash uses a 9B backbone. A fast vendor benchmark does not tell me whether that model is an efficient fit for a particular laptop. My desktop and laptop remain separate execution targets, with separate local state and verification requirements.

I am not publishing a cost-reduction percentage for this change. That needs comparable successful workloads and actual usage records. Avoided calls, estimated context savings, latency, and billed spend answer different questions.

Why this work matters to me

I want AI adoption to produce workflows people can trust and maintain. That means deciding where automation helps, connecting the right systems, protecting handoffs, and measuring whether the outcome improved.

Building this extension is one way I practice that operating discipline. The next step is to qualify live decision inference and verify the rollout on each machine. The useful proof is a system that can finish the right work, preserve what it knows, and show how the result was verified.

My professional background connects that building work to Customer Success, technical support, implementation, and operations leadership.
