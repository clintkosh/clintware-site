Portability Check

Find out whether an AI-built application actually belongs to you operationally. Portability Check is being developed as an assessment of source ownership, hosting, authentication, database, storage, email, secrets, migrations, deployment, and vendor dependencies.

Current state: methodology exists · automated checker not yet released
See the Shared Skills methodHave Clintware do it for you

Three ways through the problem

1. Check itScore the project for portability and identify the dependencies that would break or become difficult to operate if the builder subscription disappeared.
2. Fix it with a planGenerate prioritized remediation, deployment changes, environment-variable requirements, migration steps, README/EXIT documentation, and provider-specific work.
3. Have Clintware fix itTurn the assessment into a hands-on implementation engagement: move critical dependencies under infrastructure you control and leave a documented independent deployment path.

Intended output

SOURCE OWNERSHIP PASS DEPLOYMENT PASS DATABASE PASS AUTHENTICATION WARNING EMAIL PASS STORAGE FAIL SECRETS PASS MIGRATIONS WARNING DOCUMENTATION FAIL VENDOR LOCK-IN MEDIUM PORTABILITY SCORE 82 / 100

The checker should explain each finding and produce the next action, not merely a score. The service path exists to close the gap for users who do not want to perform the migration themselves.

Evidence boundary

This is currently a product candidate, not a claimed automated production scanner. The underlying portability method has already been documented as a Clintware Shared Skill. The next proof is external project assessments, repeated dependency patterns, and evidence that users request or pay for remediation.
