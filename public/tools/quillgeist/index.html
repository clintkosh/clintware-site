Quillgeist

One execution system. Local first. Cloud when useful.

Quillgeist is not two products. The direct MVP is the local workbench: type an intent, inspect what Quillgeist understood and the PowerShell it generated, then execute, verify, repair within bounded policy, or install a native local schedule. Quillgeist Cloud is an optional control plane over that same runtime for paired-device routing, remote scheduling, approvals, account history, and reporting.

One Quillgeist. Two surfaces.

Local Workbench
The direct MVP and shortest path to proving the product.Runs on localhost against the installed Quillgeist Node. Intent compilation, PowerShell preview, local execution, bounded E3 recovery, verification, and Windows-native scheduling can work without the hosted control plane. This is not a smaller fork; it is the most direct interface to the core runtime.
Quillgeist Cloud
The optional remote control plane for the same runtime.Pairs multiple Nodes, routes Execution Packs, coordinates cloud-owned or device-owned schedules, exposes approvals, and keeps account-scoped operational history. Cloud extends Quillgeist; it does not replace the local engine.
Shared engine
Both surfaces use the same local authority and execution model.Capability policy, sensitive-data checks, snapshots, rollback, Definition-of-Done verification, Result Packs, and local evidence remain authoritative at the Node.

Working in Core v0.4

Direct local intent
The local workbench compiles a bounded set of natural-language intents into inspectable execution.Current deterministic coverage includes HTTP health, Windows service/process state, Git inspection and fast-forward sync, directory state, and explicit PowerShell. Unsupported or ambiguous requests are refused instead of guessed.
Scoped rules
Operating rules can be global, project-specific, or task-specific.Older saved preferences remain backward-compatible as global rules. Keyword gates can further limit when a rule is compiled.
Selective compile
Quillgeist no longer dumps a flat preference list into every prompt.The compiler infers or accepts a task type, selects only applicable rules, and reports total rules, rules used, and estimated rule-context avoided.
Correction proposal
A correction can become an inspectable rule proposal without silently changing persistent state.The user chooses whether to save it and at what scope.
Local runtime
Windows, macOS, and Linux execution remain part of the alpha.Filesystem, processes, Python, PowerShell, Node.js, Git, tests, schedules, snapshots, rollback, and compact Result Packs remain available.
Authority
Allow / ask / never stays locally authoritative.Remote requests cannot override a local never rule; sensitive-data checks remain local before eligible execution or persistence.
Assemblerer interop
Company manifests can now compile into bounded Quillgeist team operating context.Founder authority ceiling, routing preference, pending work, and required proof are preserved without silently turning the manifest into permanent rules.
Contextor
Execution noise is compacted before returning to a reasoning model.Token reduction is treated as measured telemetry, not the product category itself.

CLI proof

Compile a direct local intent
quillgeist intent "Check https://clintware.com every hour" --autonomy safe
Open the localhost workbench
quillgeist local
Add a project rule
quillgeist-rules add "Back up production before deploying" --scope project --project Clintware
Compile a task with only applicable context
quillgeist-plan "Deploy the site" --project Clintware
Turn a correction into an unsaved proposal
quillgeist-rules propose "Never overwrite the original file" --task-type file_edit
Compile an Assemblerer team manifest
quillgeist-manifest assemblerer-export.json --plain

What still has to be proven

The direct local MVP now makes the thesis easier to test: can a user state a bounded intent once, see exactly what will run, let Quillgeist execute and verify it locally, and keep that operating method independent of whichever reasoning model they use? The Cloud layer matters when remote control, multiple devices, centralized schedules, approvals, or history are useful.

Target evidence: outside multi-model users, repeated-instruction reduction, external-context reduction, verified local task completion, successful native recurring execution, and portability across providers.
